Containers & Kernel

How Containers Work

Containers share the host OS kernel. The stack is: Linux Kernel → OS (CentOS/Fedora/Ubuntu) → Containers.

  • If the kernel is Linux, you can only run Linux containers
  • Windows runs Linux containers via WSL2 (a lightweight Linux VM)
  • You cannot natively run Linux containers on Windows or vice versa without a VM layer

Docker vs containerd

🐳 Docker

Full platform: CLI, build tools, volume management, security, auth, networking + containerd inside

⚙️ containerd

Just the container runtime — the core engine that actually runs containers

Docker: CLI → Docker Engine → containerd → containers
K8s:   kubelet → containerd → containers (cuts out the middleman)
💡 K8s only needs containerd to orchestrate containers — no need for full Docker installation. K8s dropped Docker support (dockershim) in v1.24.
🏗️

Cluster Architecture

Master Node (Control Plane)

  • kube-apiserver — Front door to the cluster; all communication flows through it
  • etcd — Key-value store holding all cluster state and config
  • controller — Runs control loops to maintain desired state (ReplicaSet, Deployment controllers)
  • scheduler — Assigns pods to nodes based on resource availability

Worker Node

  • kubelet — Agent on each node; receives instructions from API server, ensures containers are running
  • Container Runtime — Actually runs containers (containerd, CRI-O)
kube-apiserver ⟷ kubelet → containerd → containers

Pods

What is a Pod?

The smallest deployable unit in Kubernetes. A pod wraps one or more containers.

  • Containers in a pod share the same network (localhost), storage volumes, and lifecycle
  • Best practice: one main container per pod
  • Multiple containers in a pod = sidecars (helper containers)

🏍️ Sidecar Containers

▶

Like a motorcycle sidecar — a helper that rides alongside the main container:

  • Envoy proxy — handles networking/traffic
  • Log shipper (Fluentd/Filebeat) — collects and forwards logs
  • Config reloader — watches for config changes

A sidecar is a regular container inside the same pod. K8s manages it together with the main container — same scheduling, same node, same lifecycle.

🐳 Without K8s

docker run app1
docker run helper --link app1
Manual linking, fragile

☸ With K8s

Both containers in one pod — automatic shared network, volumes, lifecycle. No --link needed.

Creating a Pod

⚡ Imperative

kubectl run nginx --image nginx

--image is required — no default image!

📄 Declarative

kubectl apply -f pod.yml

Preferred for production — version controlled, repeatable

Useful Pod Commands

# List pods

# Describe (image, status, events, node)

# Quick image check

ReplicaSets

ReplicationController → ReplicaSet

ReplicationController is the old way. ReplicaSet is the modern replacement with one key addition: selector.

  • The selector with matchLabels can monitor pods created outside of the ReplicaSet
  • If you want 6 replicas and 3 matching pods already exist → only 3 more are created
  • ReplicaSet adopts existing pods with matching labels

Writing a ReplicaSet

Simple recipe: in spec.template, paste your pod's metadata + spec (without apiVersion and kind).

ReplicaSet spec → template → { pod metadata + pod spec }

🔄 Deployment Strategies

▶
StrategyBuilt-in?Downtime?How
RollingUpdate✅ DefaultNoGradually replace pods one by one
Recreate✅Yes ⚠️Kill all old, then create all new
Blue-Green❌ ManualNoDeploy new alongside old, switch service selector

RollingUpdate (default)

Old: ● ● ● ●       New:  
      ● ● ●           ○
      ● ●             ○ ○
      ●                ○ ○ ○
                      ○ ○ ○ ○ 
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1   # max pods killed at a time
      maxSurge: 1          # max extra pods created

Identifying Strategy from Logs

Use kubectl describe deployment <name> and check Events:

  • Recreate: Scale down to 0 first → then scale up
  • Rolling: Interleaved scale up and scale down

🔙 Rollouts, History & Rollback

▶

kubectl rollout manages the rollout process — it monitors and controls how updates are applied.

CommandWhat it does
rollout statusWatch live progress of the update
rollout historyView all past revisions
rollout undoRollback to previous (or specific) revision
rollout pausePause mid-rollout
rollout resumeResume a paused rollout
rollout restartTrigger a fresh rolling restart

How Rollback Works

Every revision is stored as a ReplicaSet in etcd. Old ReplicaSets are kept but scaled to 0. On rollback, K8s simply scales up the old ReplicaSet.

etcd stores:
ReplicaSet rev1 → image: nginx:1.24 (scaled to 0)
ReplicaSet rev2 → image: nginx:1.25 (scaled to 0)
ReplicaSet rev3 → image: nginx:1.26 (active)

CHANGE-CAUSE vs Actual Data

CHANGE-CAUSE

Just a human-readable annotation. K8s doesn't use it for rollback. Can be null — doesn't matter.

ReplicaSets in etcd

Full API objects with complete pod spec. This is what K8s actually uses for rollback.

Used for communication between pods inside the cluster.

Service Selector

The selector says: "Any traffic that comes to me, forward to pods with these labels."

If multiple pods match → Service load balances across them (round-robin).

Request → Service → Pod 1 (app: nginx)
                   → Pod 2 (app: nginx)  ← load balanced
                   → Pod 3 (app: nginx)

Service DNS

When you create a service, K8s creates a DNS entry automatically:

service-name.namespace.svc.cluster.local

Same namespace

Just use service-name directly

Cross namespace

Use full DNS: service-name.namespace.svc.cluster.local

CNI Plugins

Container Network Interface plugins handle pod-to-pod networking: Flannel, Calico, Cilium, Cisco ACI, VMware NSX.

💡 In managed K8s (AWS EKS, GKE, AKS), the cloud provider handles CNI for you — e.g., AWS uses its own VPC CNI plugin that assigns real VPC IPs to pods.

Namespaces

What are Namespaces?

Virtual clusters inside your K8s cluster — used to isolate and organize resources. Think of them like folders.

NamespacePurpose
defaultWhere resources go if you don't specify one
kube-systemK8s internal components (API server, scheduler, etc.)
kube-publicPublicly accessible data
kube-node-leaseNode heartbeat tracking

Creating a Namespace

⚡ Imperative

kubectl create namespace dev

📄 Declarative

apiVersion: v1
kind: Namespace
metadata:
  name: dev

Working with Namespaces

# Create resource in a namespace (CLI flag)
kubectl apply -f pod.yml --namespace dev

# Or set namespace in YAML metadata
metadata:
  name: my-pod
  namespace: dev

# Get pods from a specific namespace
kubectl get pods --namespace prod

# Get pods across ALL namespaces
kubectl get pods --all-namespaces

# Switch default namespace (no more --namespace flag needed)
kubectl config set-context --current --namespace=dev

ResourceQuota

Limit resources per namespace using kind: ResourceQuota:

apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    pods: "10"
    requests.cpu: "4"
    requests.memory: 4Gi
    limits.cpu: "8"
    limits.memory: 8Gi

Scheduling

Manual Scheduling (Binding)

If no scheduler is running, you can manually assign pods to nodes using a Binding object.

apiVersion: v1
kind: Binding
metadata:
  name: nginx              # ← this is the pod name
target:
  apiVersion: v1
  kind: Node
  name: worker-node-1      # ← assign to this node

Posted to: POST /api/v1/namespaces/default/pods/nginx/binding

🐛 Taints & Tolerations

▶

Think of it like bug spray: Taint = spray on a node (repels pods). Toleration = immunity on a pod (can tolerate the spray).

# Taint a node
kubectl taint nodes node1 app=blue:NoSchedule

# Remove a taint (add - at the end)
kubectl taint nodes node1 app=blue:NoSchedule-
# Pod with toleration
spec:
  tolerations:
    - key: "app"
      operator: "Equal"
      value: "blue"
      effect: "NoSchedule"

3 Taint Effects

EffectExisting PodsNew Pods
NoScheduleStay ✅Blocked ❌
PreferNoScheduleStay ✅Try to avoid ⚠️
NoExecuteEvicted ❌Blocked ❌

Operators

OperatorNeeds value?Meaning
EqualYesKey and value must match
ExistsNoJust the key must exist (wildcard for value)
⚠️ Taints & tolerations don't guarantee a pod goes to a specific node — they only prevent pods from going where they shouldn't. A tolerated pod can still land on a non-tainted node.
💡 The master node has a taint by default: node-role.kubernetes.io/control-plane:NoSchedule — that's why your pods never get scheduled on it.

🏷️ Node Selector

▶

Simple way to attract a pod to a labeled node.

# Step 1: Label the node
kubectl label node worker-1 size=large

# Step 2: Use nodeSelector in pod spec
spec:
  nodeSelector:
    size: large
  containers:
    - name: nginx
      image: nginx

Behavior

Node (label: size=large):
  Pod with nodeSelector: size=large → Goes here ✅
  Pod with nodeSelector: size=small → Blocked ❌
  Pod with no nodeSelector → CAN go here ✅ (no protection!)

Node (no label):
  Pod with nodeSelector: size=large → Blocked ❌ (stays Pending)
⚠️ nodeSelector only controls where the pod goes — it doesn't protect the node from other pods. Pods without nodeSelector can still land on labeled nodes.

🎯 Node Affinity

▶

Advanced version of nodeSelector — same behavior, more powerful expressions.

FeaturenodeSelectornodeAffinity
Exact match✅✅
In (multiple values)❌✅
NotIn❌✅
Exists (key only)❌✅
DoesNotExist❌✅
Gt / Lt❌✅
Preferred (soft rule)❌✅

Two Types

TypeSchedulingAfter Running
requiredDuringSchedulingIgnoredDuringExecutionMust match or stays PendingIgnore label changes
preferredDuringSchedulingIgnoredDuringExecutionTry to match, but schedule anywhereIgnore label changes
💡 required = hard rule (must match) | preferred = soft rule (try but not mandatory) | ignored = don't evict running pods if labels change later

🧭 When to Use What?

ToolPurposeDirection
nodeSelectorPin pod to a labeled node (simple)Pod → Node 🎯
nodeAffinityPin pod to a labeled node (advanced)Pod → Node 🎯
Taints & TolerationsKeep unwanted pods away from a nodeNode → repels Pods 🚫
💡 To guarantee a pod runs on a specific node and nothing else runs there — combine both: taint the node (repel others) + nodeAffinity on the pod (attract it there) + toleration on the pod (allow past the taint).

📊 Resource Requests & Limits

▶ 
spec:
  containers:
    - name: nginx
      image: nginx
      resources:
        requests:            # guaranteed minimum
          cpu: "500m"
          memory: "256Mi"
        limits:              # maximum allowed
          memory: "512Mi"    # always limit memory!
          # cpu: no limit (let it burst safely)

4 Possible Combinations

#RequestsLimitsBehavior
1❌ None❌ NoneNo reservation, no cap — pod can consume everything
2❌ None✅ SetK8s auto-sets requests = limits
3✅ Set✅ SetGuaranteed minimum + hard cap — safest ✅
4✅ Set❌ NoneGuaranteed minimum, can burst — most efficient for CPU

👹 DaemonSets

▶

Ensures one pod per node — automatically. When a new node joins, a pod is added. When a node is removed, the pod is deleted.

ReplicaSetDaemonSet
ReplicasYou specify countOne per node (automatic)
New node addedNo changePod added ✅
Node removedNo changePod removed

Common examples: kube-proxy, CNI plugins (weave/calico), log collectors (Fluentd), monitoring agents.

# No imperative command — must use YAML
# Tip: generate Deployment YAML, change kind to DaemonSet, remove replicas

kubectl get daemonsets
kubectl get ds                          # short name
kubectl describe daemonset <name>
kubectl get ds --all-namespaces
💡 From K8s v1.12+, DaemonSets use the default scheduler with nodeAffinity (instead of directly setting nodeName). This means taints, tolerations, and resource checks are all respected.

📌 Static Pods

▶

Pods managed directly by kubelet — no API server needed.

  • Place YAML files in /etc/kubernetes/manifests/ (default path)
  • Kubelet periodically monitors this directory
  • Add file → pod created. Delete file → pod deleted. Pod crashes → kubelet restarts it
  • Only pods — no services, deployments, or replicasets (kubelet only understands pods)
# Check static pod path
cat /var/lib/kubelet/config.yaml | grep staticPodPath

# Or check kubelet process
ps aux | grep kubelet | grep config

# Without API server, use crictl to see pods
crictl ps

#1 Use Case: Bootstrapping the Control Plane

This is how kubeadm starts the cluster — kubelet creates control plane components as static pods:

/etc/kubernetes/manifests/
├── kube-apiserver.yaml
├── kube-controller-manager.yaml
├── kube-scheduler.yaml
└── etcd.yaml
💡 Chicken-and-egg solved! Kubelet creates the API server as a static pod — no API server needed to start the API server.

⚖️ Priority & Preemption

▶

PriorityClass is just a name + value pair. Higher value = higher priority.

# Step 1: Create PriorityClass
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
preemptionPolicy: PreemptLowerPriority
globalDefault: false

# Step 2: Use in pod spec
spec:
  priorityClassName: high-priority
  containers:
    - name: nginx
      image: nginx
kubectl get priorityclass

Key Points

  • Only applies to pods (for Deployments, put it in the pod template)
  • globalDefault: true — pods without priorityClassName get this priority. Only one PriorityClass can be the global default

Preemption Policy

PolicyBehavior
PreemptLowerPriorityDefault — evict lower priority pods to make room
NeverDon't evict — just wait in the queue until resources free up

✏️ Editing Pods vs Deployments

Pod (limited editing)

Only 4 fields editable on a running pod:

  • spec.containers[*].image
  • spec.initContainers[*].image
  • spec.activeDeadlineSeconds
  • spec.tolerations

Everything else → delete & recreate.

Deployment (edit anything)

kubectl edit deployment my-deploy

Edit any field — K8s auto-deletes old pods and creates new ones. Much easier!

CKA Exam Tips

⚡ The --dry-run Trick (YAML Generator)

Don't write YAML from scratch! Use --dry-run=client -o yaml to generate it automatically.

Simple task? Just run it

# "Create a pod named nginx with image nginx"
kubectl run nginx --image=nginx
# Done! One command, full marks ✅

Complex task? Generate → Edit → Apply

# Step 1: Generate YAML
kubectl run nginx --image=nginx \
  --dry-run=client -o yaml > pod.yaml

# Step 2: Edit (add volumes, probes, etc.)
vi pod.yaml

# Step 3: Apply
kubectl apply -f pod.yaml

📋 Imperative Commands Cheat Sheet

▶ 
# ── Pod ──
kubectl run nginx --image=nginx                                          # create pod
kubectl run nginx --image=nginx --dry-run=client -o yaml                 # generate YAML only

# ── Pod + Service in one shot (important!) ──
kubectl run httpd --image=httpd:alpine --port=80 --expose                # creates pod + ClusterIP service 🔥

# ── Service (expose existing pod) ──
kubectl expose pod redis --port=6379 --name=redis-service --type=ClusterIP
kubectl expose pod redis --port=6379 --dry-run=client -o yaml            # generate YAML only

# ── Deployment ──
kubectl create deployment nginx --image=nginx                            # create deployment
kubectl create deployment webapp --image=kodekloud/webapp-color --replicas=3
kubectl create deployment nginx --image=nginx --dry-run=client -o yaml   # generate YAML only

# ── Save to file and edit ──
kubectl create deployment nginx --image=nginx \
  --replicas=4 --dry-run=client -o yaml > deploy.yaml                    # save to file
💡 Two flags to remember:
--dry-run=client → "pretend mode, don't create"
-o yaml → "show me the YAML output"

🔍 kubectl explain & api-resources

▶

kubectl explain — Built-in YAML docs

No need to leave the terminal — drill down into any resource's YAML structure:

kubectl explain pods                          # top-level fields
kubectl explain pods.spec                     # drill into spec
kubectl explain pods.spec.containers          # deeper
kubectl explain pods.spec.containers.image    # specific field
kubectl explain deployment.spec.replicas      # shows data type too
💡 explain shows the data type of each field — <integer>, <string>, <[]Object>, etc. Super helpful to know what value to put.

kubectl api-resources — Discover everything

Lists all resource types with short names, API group, and whether they're namespaced:

kubectl api-resources    # shows: NAME, SHORTNAMES, APIVERSION, NAMESPACED, KIND

Handy shortcuts you'll discover: po (pods), svc (services), deploy (deployments), rs (replicasets)

🔑 --dry-run=client vs --dry-run=server

FlagValidates where?Speed
--dry-run=clientLocally on your machine — no API callFast ⚡
--dry-run=serverSends to API server but doesn't createSlower but more accurate

Use client 99% of the time — it's faster and works even if the cluster is down.
